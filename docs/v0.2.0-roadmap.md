# KeybChord Pico — v0.2.0 Roadmap

Development plan for v0.2.0. This supersedes the v0.1.0 plan
([`v0.1.0-roadmap.md`](v0.1.0-roadmap.md), archived). v0.1.0 is released; the
work below adds hardware updates (a CH559 USB-host coprocessor to replace the
unreliable PIO-USB keyboard host, a power switch, TRS MIDI out, USB MIDI out),
chord patterns, a chord sequencer, macros, and a configurator UI refresh.

Open design questions are recorded inline as **[DECIDE]** and must be resolved
at each milestone's kickoff.

## 1. M11 — USB MIDI out (software)

Add a USB MIDI *device* endpoint so the instrument can drive a DAW without a
DIN/TRS cable.

- The keyboard stays on the **PIO-USB** host port (`GP0`/`GP1`). USB MIDI lives
  on the **native USB** port as a TinyUSB **composite CDC (debug log) + MIDI**
  device — so USB MIDI and serial debugging coexist (spec's "USB MIDI + serial
  debugging at the same time?" = **yes**).
- USB MIDI + DIN/TRS simultaneously = **yes**: `MidiRouter` gains a second
  output target (fan-out to DIN UART and the USB MIDI interface). Cost is a
  message copy per event; no CPU concern on the RP2040.
- **Selection is a runtime toggle** (config `midi.usb_enabled` + a keymap
  binding), consistent with the existing DIN/clock/rhythm toggles — not a
  boot-key mode.
- Revise spec §1.3 (remove the "no USB MIDI" non-goal), §3.4, §4.5, and the
  custom-configuration guide.
- **Verify:** MIDI arrives over USB on a host while DIN still transmits;
  CDC debug log keeps working; USB-MIDI-off behaves as today.

## 2. M12 — Hardware: CH559 USB host + power switch + TRS MIDI out

### 2a. Replace the PIO-USB keyboard host with a CH559 coprocessor (reliability)

The PIO-USB host (a software USB host bit-banged over PIO state machines) is
unreliable: it fails to enumerate hubs and keyboards whose descriptors exceed the
stack's small enumeration buffer, so only a subset of modern keyboards work. The
RP2040 itself is fine — only the host *port* is at fault. Replace it with a
dedicated **CH559** (WCH) — a cheap 8051 MCU with a *hardware* USB host
controller — acting as a **keyboard host coprocessor**. It enumerates the
keyboard (hubs + report/NKRO protocols), parses HID reports, and forwards key
events to the RP2040 over a UART bridge; the RP2040 stays a pure C++17 app and
keeps the dual-core split, bootloader, MIDI/LCD, and FatFS+MSC storage unchanged.

- **Form factor (decided):** bare **CH559L** (LQFP-48, hand-solderable) on the
  custom PCB, ~$1.5. It runs off its internal oscillator (no crystal needed).
  **Pre-commit gate:** validate keyboard compatibility first on a cheap breakout
  (e.g. MatzElectronics CH559 USB Host Breakout, Tindie $9.50, or the
  Electrodragon CH559 mini board $5.30) flashed with the HIDman/`atc1441` host
  firmware, plugged into the keyboards that currently fail on PIO-USB.
- **Host firmware (decided):** the CH559 side is **8051 C** (SDCC, via the
  `atc1441/CH559sdccUSBHost` fork used by HIDman — GPL-3.0, acceptable because
  it's a *separate chip* and does not contaminate the MIT RP2040 firmware). The
  fork is vendored in-tree at **`firmware/ch559/`** (git-subtree import, built
  with `make`). The RP2040 side is a new UART-bridge `InputAdapter` (C++).
- Extract the keyboard report→`KeyEvent` semantics (multi-interface selection,
  report-ID / boot-vs-NKRO parsing, modifier→usage, LED SET_REPORT) so both the
  PIO-USB adapter (legacy `pico` build) and the CH559 bridge adapter reuse them.
- Add the CH559 UART pins to `pins.h` (`GP0`/`GP1` on `Serial1`); update
  `docs/wiring.md` + `wiring.png`.
- **Verify (hardware):** enumerate a hub-connected keyboard and a long-descriptor
  keyboard that currently fail on PIO-USB; confirm key events, LEDs, and hot-plug.
  **[DECIDE]** exact UART protocol framing at kickoff.

### 2b. Power switch + 3.5 mm TRS MIDI out

BOM/wiring/spec changes only; no firmware change expected.

- Add a **power switch** in the 5 V path (between supply and `VBUS`/`VSYS`).
- Add a **3.5 mm TRS (Type-A) MIDI out** jack wired in parallel with the DIN
  current loop (same `GP8`/3V3 signal; TRS type-A: tip = pin 5, ring = pin 4,
  sleeve = pin 2 GND).
- Update `docs/wiring.md` + regenerate `wiring.png`; update spec §2 (BOM,
  connections, notes).
- **Verify:** hardware-level; confirm both DIN and TRS drive a downstream synth.

## 3. M13 — Chord patterns

User-authored patterns for playing chords — arpeggios or multiple simultaneous
notes — analogous to the existing bass patterns.

- New `ChordPattern` engine + JSON format under `/chordpatterns/*.json`
  (9+ built-ins, user files appended), 16th-note grid driven by the rhythm
  clock in lockstep with drums/bass (like bass patterns and arp sync).
- Each step = a note-degree/duration: degree indices resolve through the active
  chord's pitch classes. **[DECIDE]** exact scheme for 3-note vs 4-note chords
  (proposal: indices 0–3; index 3 = the 7th when present, else rest/wrap on a
  triad). Multi-note steps allowed (multiple degrees at once).
- Per-preset association, with a **copy-from-preset** action (configurator +
  device key). Patterns are copied, not shared.
- Flash: measure a sample pattern's JSON size; set a per-preset pattern cap and
  record the total footprint against the 512 KB budget.
- Spec §6/§8 updates; configurator pattern editor; native unit tests for degree
  resolution (3- vs 4-note) and step scheduling.

## 4. M14 — Chord sequencer

Record chord presses + timing and play them back, synced to the rhythm clock —
not a full MIDI sequencer.

- Record chord changes + timing, **quantized** to the master/rhythm clock;
  playback synced to the same clock.
- **Bar-based recording:** 1, 2, 4, or 8 bars per sequence.
- Recorded chord settings (voicing mode, up/down voicings, min interval, etc.)
  are captured; during playback each setting is **toggleable per-setting**
  between "recorded" and "live".
- Per-preset association, **not copyable**.
- Strum engine/instrument **never records or plays back** — always live.
- Flash: define the event record size (chord + timing), max events/sequence,
  and max sequences/preset; **[DECIDE]** storage layout (inline in `bankN.json`
  vs separate `/sequences/*.json`). Document resulting preset footprint.
- Spec §6/§8 updates; configurator sequence editor; native unit tests for
  quantization and recorded-vs-live toggling.

## 5. M15 — Macros

One-key recall of a bundle of settings/values/actions, per-preset, configured in
the configurator.

- **Top-row `1–0` is selectable per preset** between strum and macro keys;
  the numpad remains the strum plate. `Super+1`…`Super+8` still loads presets.
- A macro = an ordered list of `set` / `toggle` / `cycle` / `inc` / `dec`
  parameter actions plus per-piece `drum_mute`, reusing the existing parameter
  model. Example: mute rhythm, mute kick, set BPM to 88.
- Per-preset; **16 commands/key and 48 commands/preset** (the firmware truncates
  excess; the configurator rejects it) to stay within the 512 KB flash budget.
- Spec §4.2/§5.2/§8.2 updates; configurator macro editor; native unit tests
  applying macros against the parameter model.

## Cross-cutting

- **Flash budget (512 KB FatFS)** is measured and documented at M13–M15; each
  feature adds per-preset JSON, so a single budget table is maintained here.
- **Spec stays the source of truth** (`KeybChord_Pico_Spec.md`); README, wiring,
  and custom-config guide updated at each milestone.
- **Tests:** every milestone keeps the native GoogleTest suite green and adds
  coverage; the configurator adds `pytest` coverage.
- **Hardware changes (M12)** are electrically independent and can proceed in
  parallel with the software milestones.
- **Storage is unchanged by M12:** the RP2040 stays, so config/presets/patterns
  remain on the onboard FatFS + MSC drag-drop drive (no MTP migration needed).
  The keyboard-host swap (2a) touches only the USB *input* path.

### Milestone ordering

M11 (USB MIDI, software) → M12 (hardware, parallel-able) → M13 (patterns) →
M14 (sequencer) → M15 (macros) → M16 (configurator). M13–M15 are ordered by
dependency: patterns (M13) precede the sequencer (M14), which records chord
behavior including patterns; macros (M15) depend only on the parameter model and
can begin after M13.
