the evidence that justified them. The roadmap remains authoritative for scope

- Every open `[DECIDE]` item in the roadmap maps to one row below.
- `Status` is one of **Open**, **Measuring**, **Decided**, or **Deferred**
  (deferred rows must name the milestone and owner that will decide them).
- A row may only move to **Decided** when its evidence is recorded in the
  bench log or the linked document.
- Do not silently change a decision; append the change and the reason.

## D1 — Pico variant and socket (M18 1a)

**Context:** v0.3 uses a socketed Pico module on the main PCB instead of the
v0.2 Pico daughter board. Board height, enclosure clearance,
insertion/removal access, and micro-USB strain relief all depend on this.

**Options**

| Option | Pros | Cons |
|--------|------|------|
| Pico H (pre-soldered headers) + female socket | No header soldering at assembly; robust; easy replacement | Taller stack; header length fixed |
| Standard Pico + purchased male headers + female socket | Cheapest module; header length selectable | Extra assembly step; solder quality risk |
| Direct solder / castellated | Lowest profile | Not socketed; contradicts fixed decision |

**Recommendation:** Pico H plus a 2×20, 2.54 mm female socket. Measure the
stack height against the enclosure and confirm the micro-USB connector can be
reached with the board installed.

**Evidence needed**

- Overall board-to-lid clearance with the chosen enclosure.
- 25+ insert/remove cycles with no bent pins or intermittent contacts.
- USB enumeration after each of the first 5 cycles.
- Strain-relief concept for the micro-USB cable.

**Exit criteria:** variant and socket part number fixed; height/clearance
drawing recorded; factory flow agreed (PCBA places socket; Pico programmed
separately and inserted at final test).

## D2 — CH559 USB port sharing, reset, and BOOT/header (M18 1b)

**Context:** the USB-A keyboard receptacle must serve as the CH559 host port
in normal use and as the CH559 device/bootloader port for flashing. Reusing an
A receptacle for device mode requires an A-to-A cable or USB-A plug breakout,
which is a cabling hazard, and VBUS direction changes between modes.

**Options**

| Option | Pros | Cons |
|--------|------|------|
| DPDT switch routes D+/D- to HP/HM (host) or DP/DM (device); `P4.6` grounded in device mode | Meets the fixed decision; one receptacle | A-to-A hazard; VBUS back-feed protection required; switch must be labeled clearly |
| Separate device port (e.g. USB-C/micro-B) | Safe, conventional, simplest power topology | Deviates from the fixed decision; second connector and board area |
| USB mux IC with mode select | Cleaner signal integrity; single control | Extra part/cost; still needs the cabling solution |

**Recommendation:** prototype the shared-A DPDT switch first. Commit to it only
if the A-to-A hazard can be eliminated with a labeled, keyed adapter and
back-feed protection. Otherwise fall back to a separate device port and record
the deviation here.

**Power/back-feed rule:** host mode sources 5 V to the keyboard; device mode is
powered by the PC. Add a power mux/ideal-diode arrangement so neither source
back-feeds the other. Do not inject regulated 5 V into `VSYS` while native USB
is connected.

**Reset:** add a deterministic CH559 reset path (RC + button or supervisor) so
bootloader entry does not depend on power-cycling. Decide whether the v0.2
BOOT button and 4-pin programming header remain as fallbacks or are removed.

**Evidence needed**

- Keyboard enumeration and key forwarding in host mode.
- CH559 bootloader enumeration and a successful `ch55xtool` flash in device
  mode.
- No back-feed measured on both VBUS paths.
- 20+ mode switches with no damage or enumeration failure.
- Documented safe cable/adapter and switch labeling.

**Exit criteria:** switch/mux part fixed; VBUS topology drawn; reset method
fixed; BOOT/header retention decided; flashing procedure documented.

## D3 — FatFS partition size (M18 1d)

**Context:** the Pico has 2 MB QSPI flash. v0.2 uses a 0.5 MB filesystem. The
v0.3 storage table assumes 1 MB to fit both sequencer families plus patterns.

**Options**

| Option | Sketch space | Filesystem | Notes |
|--------|-------------:|-----------:|-------|
| 0.5 MB (current) | ~1.5 MB | ~0.47 MB usable | Not enough for the v0.3 worst case |
| 1 MB (recommended) | ~1.02 MB | ~0.97 MB usable | Meets the roadmap budget with ~241 KB free |
| 1.5 MB | ~0.52 MB | ~1.47 MB usable | Tight sketch space; no need unless M22 exceeds budget |

**Recommendation:** 1 MB. Build and measure before locking. Revisit only if the
M20–M22 build or the worst-case storage test does not fit.

**Measured 2026-11-13**

| Measurement | Value |
|-------------|------:|
| Firmware `.bin` (`pico`) | 313,832 B (~307 KB) |
| Flash used, PlatformIO (`pico`) | 301,796 B of 1,044,480 B (28.9%) |
| Free sketch space | 742,684 B (~725 KB) |
| Firmware `.bin` (`testhook`) | 315,368 B (~308 KB) |
| Flash used, PlatformIO (`testhook`) | 303,332 B of 1,044,480 B (29.0%) |
| RAM used (`pico`) | 23,136 B of 262,144 B (8.8%) |
| Native tests | 638/638 pass |

Usable FatFS space after FTL/FAT remains an estimate (~972 KB) until measured on
hardware.

**v0.2 detection/backup/migration mechanism**

Add a top-level `"schema": 3` marker to `config.json`, each
`presets/bank<N>.json`, and `keymap.json` in v0.3. On boot, if the marker is
absent, snapshot the recognised files to `/backup/v0.2/` (preserving the
relative path) once, then apply the v0.3 defaults/aliases and rewrite the files
with the marker. Sequence files keep their existing `"version": 1`; pattern
files are unaffected by the freestyle rename. This mirrors the existing
`migrateLegacyPresetBanks` boot migration and avoids content-sniffing false
positives. Implement alongside M21.

**Remaining evidence:** worst-case storage test for both sequencer families at
M22.

**Exit criteria:** partition size fixed in `platformio.ini` (done); measured
headroom recorded (done); migration mechanism chosen (done); M22 worst case
guarded.

## D4 — Freestyle sequence file layout (M22)

**Context:** the freestyle sequencer needs per-preset, 10-slot storage. The
roadmap proposes separate files but leaves room for sharing the chord sequence
file.

**Recommendation:** start with separate `/freestyle/b<N>p<M>.json` files, all
ten slots per preset, compact JSON, immediate saves, missing/corrupt = empty.
Re-evaluate against the measured storage budget at M22 kickoff.

**Status:** deferred to M22. No M18 hardware dependency.

## D5 — Graphics stack and font licensing (M18 1c)

**Context:** the SSD1309 needs text + graphics + partial updates. The existing
`DisplayManager`/`LcdAdapter` API is text-only (2×16). Flash cost, font
licensing, and refresh behavior decide the choice.

**Options**

| Option | Pros | Cons |
|--------|------|------|
| In-house text+graphics layer | Minimal flash; full control of partial updates; no license risk | More code to write/test |
| U8g2 (or similar) | Mature fonts/primitives | Flash cost; configure to avoid pulling unused fonts; license review |
| Other graphics library | Feature fit | Same flash/license review; porting work |

**Recommendation:** prototype the in-house layer first because the screen set is
small and fixed. Switch only if the library's flash and font licensing are
clearly better after measurement.

**Order:** one finished 4-pin I2C module from AliExpress placed **2026-11-13**.
Bench measurements are pending delivery. On arrival, record the exact listing
and verify the controller marking (SSD1309), 3.3 V operation, pin order, and I2C
address (`0x3C`/`0x3D`).

**Evidence needed**

- Full-frame and dirty-region update times at 400 kHz.
- No MIDI/playback stalls during worst-case updates.
- Flash delta for the chosen stack.
- Font license note in `THIRD_PARTY_LICENSES.md` if a library/font is used.
- Readability at the intended enclosure distance and angle.

**Exit criteria:** stack chosen; refresh budget documented; license recorded.

## D7 — Board dimensions, mounting, enclosure, placement (M19 input)

**Context:** no `.kicad_pcb` exists yet. Outline, mounting holes, screen window,
switch access, and connector placement all need a mechanical target before
layout.

**Recommendation:** choose the enclosure or define a board outline with a
screen window and switch access before M19 layout starts. Keep the Pico socket,
USB-A receptacle, DIN/TRS, and power connector as mechanically stressed THT
parts.

**Evidence needed:** outline drawing, mounting-hole pattern, screen window
dimensions, connector edge positions, switch access, Pico insertion clearance.

**Exit criteria:** mechanical constraint drawing attached to the M19 kickoff.

## D8 — Test-bed fixture form factor and CI (M18 1e)

**Recommendation:** a bench Pico running a TinyUSB HID keyboard emulator with
selectable boot/NKRO descriptors, a real USB hub, CH559 UART capture, DIN/USB
MIDI capture, and display readback via the `testhook` mirror. Run locally by
default; self-hosted CI only if it proves stable.

**Evidence needed:** repeatable key injection, display frame readback, MIDI
timestamping, and documented limitations (low-speed devices, hubs, wireless
dongles, descriptor edge cases).

**Exit criteria:** fixture form factor and CI decision recorded; harness
prototype demonstrated.
