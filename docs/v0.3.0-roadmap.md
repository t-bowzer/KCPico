# KeybChord Pico — v0.3.0 Roadmap

Development plan for v0.3.0. This supersedes the v0.2.0 plan
([`v0.2.0-roadmap.md`](v0.2.0-roadmap.md), archived). v0.3.0 is a clean-break
hardware release built around a **socketed Raspberry Pi Pico module** on a new
single main PCB, a **2.42" 128x64 SSD1309 I2C OLED**, a CH559 USB host/device
switch for keyboard use and CH559 flashing, a **freestyle** rename of the strum
pad, a freestyle sequencer, an onboard keymap editor, and a hardware test bed.
v0.2 hardware is not supported. v0.2 JSON data is migrated.

A direct-RP2040 / 4 MB / USB-C production design is intentionally **not** part of
v0.3.0. It is deferred to a separate roadmap once volume, sourcing, or board-size
needs justify the additional NRE, assembly, and test work.

Open design questions are recorded inline as **[DECIDE]** and must be resolved
at each milestone's kickoff.

## Fixed decisions

- **Hardware:** new single main PCB; v0.2 Pico daughter board and LCD1602
  hardware are unsupported.
- **Compute:** socketed Raspberry Pi Pico module (RP2040, 2 MB flash,
  micro-USB). Use a female header socket on the main PCB; insert a Pico H or a
  standard Pico with headers at final assembly. **[DECIDE]** exact Pico variant
  and socket part at M18.
- **Display:** 2.42" 128x64 SSD1309 I2C OLED. The LCD1602/PCF8574 path is removed
  from release builds.
- **CH559 flashing:** reuse the USB-A keyboard receptacle with a switch that
  selects CH559 host vs device mode and grounds `P4.6` for bootloader entry.
  Add a CH559 reset path; whether the BOOT button/programming header remain is
  a qualification decision.
- **Freestyle:** rename only. The pad keeps the current chord-derived strum
  behavior. Rename UI, docs, code identifiers, keymap menu names, and JSON; load
  v0.2 `strum` aliases and rewrite as `freestyle` on save.
- **Freestyle sequencer:** records absolute note/velocity/duration/channel
  events, independent of the current chord. Capacity mirrors the chord
  sequencer: per-preset, 10 slots, 1/2/4/8 bars, max 64 events. Freestyle and
  chord sequences may play simultaneously.
- **Onboard configurator:** keymap learn mode is committed. On-device macro
  editing is a timeboxed investigation with a go/no-go gate, not a committed
  feature.
- **Testing:** local hardware test bed with optional self-hosted CI. Targets are
  NFR-1 key-to-MIDI latency <10 ms and NFR-2 rhythm/arp jitter <2 ms.
- **Release model:** DIY/open-source. No FCC/CE certification is planned. Use
  EMC-conscious design and clear disclaimers; sellers of assembled kits remain
  responsible for their local compliance obligations.
- **Volume:** design for a 5–10 unit prototype run, then a 500–2,000 unit
  pilot/production run. Direct RP2040 is not expected to be cost-effective in
  that band; revisit it in the separate production-hardware roadmap.

## Flash and storage budget (v0.3.0)

The Pico has 2 MB of QSPI flash. Current firmware is ~307 KB (`.bin`). Set the
FatFS partition to **1 MB** (`board_build.filesystem_size = 1m`), which leaves
~1.02 MB for the sketch after EEPROM/flash overhead. That is sufficient for the
current firmware and planned growth; **[DECIDE]** at M18 if a different split is
needed after measuring the M20–M22 build.

The filesystem has ~972 KB usable after FTL/FAT overhead. Sequence and pattern
files use compact JSON; other files are pretty-printed.

| Item | Worst-case footprint |
|------|---------------------:|
| 5 preset banks × 8 slots | ~64 KB |
| Built-in rhythm/bass/chord patterns | ~24 KB |
| User-created rhythm/bass/chord patterns | ~48 KB |
| `config.json` + `keymap.json` | ~9 KB |
| Chord sequences (40 presets × 10 slots × 64 events) | ~280 KB |
| Freestyle sequences (40 presets × 10 slots × 64 events) | ~300 KB |
| FAT/directories | ~6 KB |
| **Total** | **~731 KB** |
| **Free** | **~241 KB** |

Firmware is outside the FatFS partition: ~307 KB of ~1.02 MB sketch space.

Freestyle sequence size is an estimate until the M22 serializer is implemented.
Add a native worst-case test and re-measure both sequence families. If the 1 MB
filesystem cannot hold both at full capacity, cap freestyle slots/events for
v0.3.0 and expand the limits on the deferred 4 MB production design.

## 0. Pre-0.3 (completed)

- v0.2.0 tagged and released.

## 1. M18 — Architecture, cost, and prototype gates

Resolve the decisions that would be expensive to change after layout. This
milestone is mostly prototypes, measurements, and quotes; no production hardware
is ordered.

### 1a. Pico mounting and assembly

- Choose the exact Pico variant (Pico H with pre-soldered headers vs standard
  Pico plus purchased headers) and the female socket part.
- Confirm board height, enclosure clearance, insertion/removal access, and
  strain relief for the micro-USB connector.
- Decide whether the Pico is inserted at final test/packaging or shipped loose
  with the kit.
- Define the factory flow: PCBA places the socket and all SMT/THT parts; the
  Pico is programmed separately via BOOTSEL or SWD, then inserted and tested.
- **Verify:** a socketed Pico enumerates USB, runs the firmware, and survives
  repeated insertion/removal.

### 1b. CH559 USB port sharing

- Prototype the USB-A switch: host mode routes D+/D- to CH559 `HP`/`HM`;
  device mode routes them to CH559 `DP`/`DM`, grounds `P4.6`, and presents the
  CH559 bootloader to a PC.
- Define VBUS direction and back-feed protection. In host mode the board powers
  the keyboard; in device mode the PC supplies VBUS to the CH559. Do not allow
  either source to back-feed the other.
- Add a CH559 reset path so bootloader entry is deterministic. Decide whether
  the existing BOOT button and 4-pin programming header remain as fallbacks or
  are removed.
- Address the cabling hazard: reusing a USB-A host receptacle for device mode
  requires an A-to-A cable or USB-A plug breakout. Specify the safe cable/adapter
  and label the switch position. If this cannot be made acceptably safe, fall
  back to a separate device port before layout.
- **Verify:** keyboard enumeration in host mode; CH559 bootloader enumeration
  and flashing in device mode; no back-feed; repeated switching without damage.

### 1c. OLED selection and refresh budget

- Confirm the 2.42" SSD1309 128x64 I2C module: controller, address, 3.3 V
  operation, backlight/charge-pump current, connector/pinout, and mechanical
  fit.
- Benchmark full-frame and dirty-region updates at 400 kHz. A full 128x64 frame
  is ~1 KB, or ~23 ms at 400 kHz; menus and pattern grids must use partial
  updates and rate limiting.
- Decide the graphics stack: minimal in-house text+graphics layer vs an existing
  library. Account for flash cost, font licensing, and the existing text-based
  `DisplayManager`/`LcdAdapter` API.
- **Verify:** readability at the intended enclosure distance/angle; update time
  measured; no MIDI/playback stalls.

### 1d. Filesystem and storage budget

- Set `board_build.filesystem_size = 1m` and confirm the firmware still has
  comfortable sketch headroom.
- Re-check the v0.2 storage table plus the freestyle estimate; identify the
  worst-case per-file sizes and any caps needed.
- Decide how v0.2 files are detected, backed up, and migrated.

### 1e. Test-bed feasibility

- Prototype a Pico as a TinyUSB HID keyboard emulator (boot and NKRO report
  descriptors). Confirm the CH559 enumerates it and forwards key events.
- Identify limitations: low-speed devices, hubs, wireless dongles, and
  descriptor edge cases. Plan a real hub and a descriptor-matrix fixture.
- Confirm display readback via a `testhook` mirror rather than camera/OCR, and
  MIDI timing capture via a hardware timer or logic analyzer.
- **Verify:** repeatable key injection, display frame readback, and MIDI
  timestamping on the bench.

### 1f. Cost and manufacturing gate

- Build a loaded-cost comparison at 500–2,000 units: Pico module + headers/socket
  + assembly/test vs the deferred direct-RP2040 design. Include consignment,
  handling, yield, and test time.
- Confirm the PCBA partner can place the Pico socket, THT connectors, CH559, and
  OLED header, and can handle the 5–10 prototype and 500–2,000 pilot quantities.
- Exit with a fixed BOM, schematic blocks, board outline, and go/no-go decisions
  for 1a–1e.

## 2. M19 — Hardware rev A

### 2a. Single main PCB

- Replace the current Pico daughter-board schematic with a single main PCB:
  Pico socket, CH559, USB-A host/device switch, OLED header, DIN/TRS MIDI out,
  power input, and the existing keyboard/DIN wiring.
- Create the PCB layout (no `.kicad_pcb` exists today), including board outline,
  mounting holes, connector placement, screen window/clearance, and switch
  access.
- Use SMT for passives and ICs; keep the Pico socket and mechanically stressed
  connectors as THT. Update footprints and 3D models.
- Add fiducials, tooling holes, test points, and clearly labeled programming/
  debug pads.

### 2b. BOM, PCBA, and factory flow

- Produce an LCSC/JLCPCB-compatible BOM and CPL. Identify basic vs extended
  parts, second sources, and lifecycle risks.
- Build 5–10 prototypes. Then plan a 500–2,000 unit pilot/production run with a
  PCBA partner.
- PCBA places the Pico socket and all board parts. The Pico is sourced
  separately, programmed via BOOTSEL or SWD, inserted at final assembly, and
  tested.
- Document assembly drawings, polarization, connector orientation, and the CH559
  flashing procedure.

### 2c. Bring-up

- Verify power rails, Pico boot, native USB CDC/MIDI/MSC, OLED, CH559
  enumeration, keyboard input, LEDs, DIN/TRS MIDI, storage, and boot keys.
- Run the M24 smoke tests as they become available.
- **Verify:** 5–10 assembled boards pass bring-up; known issues are documented.

## 3. M20 — Display/UI foundation

Replace the text-only 2x16 display model with a display abstraction that can
render both text and graphics on the SSD1309. This is the foundation for every
menu, editor, and status screen; it must land before the freestyle sequencer and
onboard keymap editor work.

- Add an OLED adapter/driver (SSD1309, I2C) behind the existing display adapter
  interface or a new `DisplayAdapter` abstraction.
- Provide text and graphics primitives, a font, clipping, and dirty-region/
  partial-update support.
- Rework `DisplayManager` into a screen model that covers idle, menus, value
  edit, prompts, name edit, errors, info, persistent status, pattern grids, and
  sequence status.
- Preserve the existing behavior and messages where practical; remove the
  LCD1602 path from release builds but keep a fake/recording display adapter for
  native tests.
- Add a `testhook`-only display mirror command (frame text or framebuffer hash)
  for the hardware test bed.
- Add native layout tests for each screen and hardware checks for readability,
  refresh time, and playback interference.
- **Verify:** all existing screens reimplemented; display updates never delay
  due playback; refresh budget documented.

## 4. M21 — Freestyle rename and migration

Rename the strum pad to the freestyle pad without changing its behavior.

- Rename user-facing text, menu titles, keymap labels, docs, and configurator
  UI from "Strum" to "Freestyle".
- Rename code identifiers and files as appropriate (`StrumEngine`,
  `StrumParams`, `strum_engine.*`, tests) while keeping the behavior identical.
- Rename JSON fields/enums and the `open_menu` name from `strum` to `freestyle`.
  Load v0.2 `strum` aliases, log/backup the migration, and write `freestyle` on
  save.
- Update configurator models, validation, keymap diagram, macros, and tests.
- Update the spec, custom-configuration guide, README, AGENTS notes, and JSON
  skill references.
- **Verify:** v0.2 config/presets/keymaps load and round-trip; existing strum
  behavior is unchanged; all native and configurator tests pass.

## 5. M22 — Freestyle sequencer

Record and loop freestyle pad performances as absolute MIDI notes, independent of
the active chord. The chord sequencer remains chord-based; both may play at the
same time.

- **Model:** note-on/note-off (or note + duration), velocity, channel, and step.
  Polyphonic. Playback does not re-resolve against the current chord or pad
  settings.
- **Capacity:** per preset, 10 slots, 1/2/4/8 bars, max 64 events, matching the
  chord sequencer.
- **Storage:** choose the file layout at kickoff. Proposal: separate
  `/freestyle/b<N>p<M>.json` files, all ten slots per preset, compact JSON, with
  immediate saves. A missing/corrupt file loads empty. Preset Clear removes the
  file. **[DECIDE]** whether to share a file with chord sequences instead.
- **Recording:** count-in on the rhythm clock, quantize to 1/4, 1/8, or 1/16,
  overdub vs replace policy, auto-stop after the selected bars, and live pad
  input override behavior.
- **Playback:** loop from the next bar, start/stop/clear controls, live freestyle
  pads still available, and defined mixing with chord-sequence playback (note
  conflicts, live chord wins, stop/start independence).
- **Controls:** new keymap actions and slot selection; avoid conflicts with the
  chord sequencer (`Ctrl+F9`–`Ctrl+F12`, `Ctrl+1`–`Ctrl+0`) and pattern editors.
  All actions rebindable.
- **UI:** recording/playback status screens on the OLED, slot/bar selection, and
  clear/overwrite prompts.
- **Configurator:** model, serializer, validation, and a freestyle sequence
  editor mirroring the chord sequence tab.
- **Tests:** native model/serializer/engine/keymap tests, configurator pytest
  tests, worst-case storage test, and a hardware checklist.
- **Verify:** both sequencers play simultaneously; timing meets NFR-2; the
  storage budget holds at full capacity.

## 6. M23 — Onboard keymap editor and macro spike

### 6a. On-device keymap assignment

- Add a keymap learn mode: choose an action/parameter, press a key or combo, and
  assign it.
- Cover all remappable keymap actions, including the freestyle name change,
  sequence controls, pattern-editor entry, and pad mappings where applicable.
- Enforce reserved keys and boot keys (`Esc`, `Ctrl` at power-on, `Ctrl+number`,
  panic, etc.) and define conflict behavior (reject, replace, or clear the old
  binding).
- Save `keymap.json` atomically, reload the live keymap, and provide reset-to-
  defaults.
- Update the configurator keymap model/validator so on-device edits round-trip.
- **Verify:** remap keys without a PC; invalid/conflict handling is clear;
  factory reset restores defaults.

### 6b. Macro configuration spike

- Timebox an investigation of on-device macro editing: command selection,
  ordering, values, per-key/per-preset limits, LCD/UI flow, and storage.
- Decide go/no-go. If no-go, keep macro editing in the configurator and document
  the decision. If go, add a follow-up milestone rather than expanding v0.3.0
  without re-planning.
- **Verify:** a written recommendation with estimated effort, flash/UI cost, and
  risks.

## 7. M24 — Hardware test bed and timing

Build a repeatable fixture that drives keyboard input and observes MIDI and
display output.

### 7a. Fixture

- Pico-based TinyUSB HID keyboard emulator with selectable boot/NKRO and custom
  report descriptors.
- Real USB hub, VBUS/hot-plug control, and CH559 UART capture.
- DIN MIDI capture and native USB MIDI capture.
- OLED readback via the `testhook` display mirror; optional I2C/SPI sniffing for
  debugging.
- Pico programming via BOOTSEL/SWD and CH559 flashing via the new switch.

### 7b. Automated scenarios

- Cover chords, freestyle pads, both sequencers, patterns, MIDI clock, USB MIDI,
  MSC, boot keys, panic, and keymap edits.
- Reuse and extend `tools/midi_test/` where practical; add pytest scenarios and
  artifact capture.
- Run locally by default; optional self-hosted CI.

### 7c. Timing

- Measure key-to-MIDI latency (NFR-1 <10 ms), rhythm/arp jitter (NFR-2 <2 ms),
  sequencer timing, and USB-vs-DIN skew.
- Capture timestamps with a hardware timer or logic analyzer, not host USB
  scheduling timestamps.
- Report min/median/p99/max over repeated runs at multiple tempos and loads.
- **Verify:** repeatable pass/fail and a timing report; failures are actionable.

## Cross-cutting

- **Compatibility:** v0.2 hardware is unsupported. v0.2 JSON is migrated with
  aliases and a backup. The freestyle rename is behavior-preserving.
- **Storage:** the 1 MB FatFS budget above; M18/M22 must measure and guard the
  worst case. If both sequencers do not fit at full capacity, cap freestyle for
  v0.3.0 and expand later.
- **Testing:** keep the native GoogleTest suite green and add coverage next to
  each change; keep configurator pytest coverage; add hardware checklists and the
  HIL harness. `testhook` stays out of release builds.
- **Configurator parity:** firmware models and validators are mirrored in the
  configurator; update both sides for the freestyle rename, sequencer, and
  keymap editor.
- **Manufacturing:** 5–10 prototypes, then a 500–2,000 unit pilot. The Pico is
  socketed and inserted at final assembly; the board is not fully SMT. THT
  connectors and the Pico socket are expected.
- **Compliance:** DIY/open-source release, no FCC/CE certification. Use ESD
  protection, USB VBUS/back-feed protection, and EMC-conscious layout; include
  disclaimers for kit sellers.
- **Deferred:** direct RP2040, 4 MB flash, USB-C, all-SMT assembly, and formal
  certification belong to a separate production-hardware roadmap. Revisit when
  volume reaches roughly 5,000+, Pico sourcing/assembly becomes painful, or the
  size/4 MB/USB-C benefits become necessary.

### Milestone ordering

M18 (decisions/prototypes) → M19 (hardware rev A) can proceed in parallel with
M20 (display/UI) and M21 (rename). M22 depends on M20/M21; M23 depends on M20/M21;
M24 starts during M18 and runs through release. M25 is last. Hardware assembly
and firmware work can overlap, but the OLED/UI foundation must land before the
freestyle sequencer and onboard keymap editor are considered complete.

### Open `[DECIDE]` items

- Exact Pico variant (Pico H vs Pico + headers) and female socket part.
- CH559 switch part, reset method, and whether the BOOT button/programming header
  remain.
- 1 MB FatFS split vs a different partition size after M20–M22 measurements.
- Freestyle sequence file location/schema (separate files vs shared sequence
  file).
- Graphics stack (minimal in-house vs library) and font licensing.
- Macro spike outcome: defer, or add a follow-up milestone.
- Board dimensions, mounting holes, enclosure, and screen/switch/connector
  placement.
- Test-bed fixture form factor and optional CI runner.
- Release date and whether any item is a stretch goal.
